# v0.4 の高速化

XVI / 68000 / 16 MHz / 12 MB の実機 HDS で、1 周約 2 時間になる見込みとの報告を受け、通常 RAM の検査ループを最適化しました。実機での最適化後の所要時間はまだ測定していません。

## 実装

Human68k / FD / HDS で共通の MC68000 アセンブリカーネルを使います。kind・action・方向の分岐はチャンク入口だけで行い、定数反転の正常経路は次の 5 命令です。

```asm
loop:
    move.l (a0),d1
    cmp.l  d0,d1
    bne.s  error
    move.l d2,(a0)+
    dbra   d7,loop
```

定数の書き込みは `move.l` / `dbra` の 2 命令、照合は 4 命令です。降順、アドレス、乱数、分散 Walking、バイト / ワード書き込みも専用ループを使用します。テスト RAM へは longword ごとに順番どおりアクセスし、March C- の read → write 順序を維持します。

進捗は C 側で 4096 語単位に集計します。不一致のときだけ C のコールバックへ戻り、元の報告値・カウンタ飽和・通知後の反転書込みを維持して残りから再開します。中断通知の位置も従来と同じです。

乱数の xorshift は XOR に対して線形なので、アドレスを下位 10 ビットと残りに分けても期待値は同一です。下位部分は 256 longword / 1 KiB の変換表、上位部分と seed はチャンク入口で計算します。乱数カーネルは 1 KiB 境界までを処理しますが、進捗通知は従来どおり全ブロック合計の 4096 語ごとです。C 参照実装は表を使用せず毎語計算し、両者を照合します。

## Walking の方式

| 方式 | Test 4 の走査数 | 1 周での各アドレスの内容 |
| --- | --- | --- |
| 分散（既定） | 4 | アドレスでずらした単一ビットとその補数 |
| 従来の全 32 ビット | 128 | 全 32 ビットそれぞれの単一ビットと補数 |

分散方式は `1 << (((address >> 2) + seed) & 31)` を使います。開始ビットは周回ごとに一つ進み、Walking を含む同じ選択で 32 周連続実行すると各アドレスで全 32 ビットを実施します。隣接 32 語には全 32 種類のビットが分布します。**分散方式の 1 周と、従来方式の 1 周は同じ検査内容ではありません。**

通常 RAM の全 7 項目の合計は 166 → 42 走査になります。単独起動版の低位 Test 8 は別に同じ 6 パターンを実行します。

設定画面の `w` で方式を切り替えます。Human68k は起動引数 `--full-walking` でも従来方式を指定できます。設定変更は次の Pass から反映されます。途中の Pass は既存方式で完了します。

## 同条件での測定

2026-11-26、XEiJ 0.26.10.08 / XVI / 68000 / 16 MHz / RAM 1 MiB、Linux aarch64 / Temurin 26 / Xvfb 上で測定しました。検査範囲は `$10000` から **64 KiB**、seed は `68c0ffee`、各 1 周です。進捗・描画コールバックは使いません。ROM IOCS `_ONTIME` の 1/100 秒単位で各項目を計測しています。

| 検査 | 旧 C 版（従来 Walking） | ASM（従来 Walking） | ASM（分散 Walking） |
| --- | ---: | ---: | ---: |
| 1 アドレス | 1.30 秒 | 0.20 秒 | 0.19 秒 |
| 2 全 0 / 全 1 反転 | 2.59 秒 | 0.33 秒 | 0.33 秒 |
| 3 チェッカーボード | 2.59 秒 | 0.33 秒 | 0.34 秒 |
| 4 Walking | 41.45 秒 | 5.36 秒 | 0.24 秒 |
| 5 疑似乱数 | 3.86 秒 | 0.77 秒 | 0.78 秒 |
| 6 March C- | 2.02 秒 | 0.27 秒 | 0.27 秒 |
| 7 Byte / word | 1.46 秒 | 0.16 秒 | 0.15 秒 |
| **合計** | **55.27 秒** | **7.42 秒** | **2.30 秒** |

従来 Walking を保って約 7.4 倍、分散 Walking では約 24 倍です。分散方式の差には走査数の削減を含みます。乱数変換表を入れる前の ASM は疑似乱数が 1.45 秒だったため、表によってその部分をさらに約 1.9 倍にしました。

これは描画を除く検査エンジンの小領域測定です。Test 8、12 MiB 全域、UI、実機のメモリボードのウェイトを含む所要時間ではありません。実機の完了予想へそのまま換算しないでください。生の計測値と SHA-256 は [測定結果 JSON](results/performance-v04/) に保存しています。旧 C 版は `ac7f130` のエンジンです。

## 再現・照合

```sh
make check
make test-native RUN68=/path/to/run68
make build/bench-engine.xdf
xvfb-run -a -s '-screen 0 1280x1024x24' python3 tools/bench_xeij.py \
  --xeij /path/to/XEiJ.jar --elf build/bench_engine.elf \
  --image build/bench-engine.xdf --output build/bench/current
```

ベンチマークは分散方式と従来方式を順に測定します。`tools/bench_engine.c` は `MT_BENCH_BASELINE` を指定すると旧 `mt_run` API のみで測定でき、旧 C エンジンにリンクした ELF / XDF も同じ `bench_xeij.py` で実行できます。

`test-native` は実際の 68000 バイナリを run68x で実行します。ホスト ASan / UBSan テストに加え、ASM と別コンパイルの C 参照実装を同じアドレスで比較します。1 / 31 / 4095 / 4096 / 4097 / 8193 語、複数領域、複数 seed、正常・故障注入・中断の 144 ケースで、途中の RAM 内容、昇順・降順、報告値と順序、通知位置、エラー数飽和、境界外保護を確認します。従来 Walking と分散 Walking の両方を含みます。
